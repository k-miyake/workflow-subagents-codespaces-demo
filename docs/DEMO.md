# デモの進行台本

## 開始前

`./demo doctor` を確認し、`./demo verify --timeout 600` の実モデル E2E を一度通す。ターミナル A で `./demo start` を起動し、8082 と 8000 の PORTS を開く。前回の HTML を表示する場合は前回の結果だと説明する。

## 1. 何を見せるか（約 30 秒）

「Queue に複数 PR の調査依頼を入れると、モデルがその場で計画を作り、Durable Functions が処理します。PR の状態はサンプルの模擬データです。エージェントとワークフローは実際に動きます。」

## 2. コーディネーターを見る（約 1 分）

`src/main.agent.md` を開く。`workflows.enabled: true` と `workflows.subagents` の 2 種類のスペシャリストを示す。末尾の説明が「各 PR を並列分析 → 全結果をレポートに統合 → Blob 保存」の意図を指示していることを説明する。静的な DAG の JSON をアプリに埋め込んでいない点が見どころ。

## 3. 実行する（生成時間に応じる）

ターミナル B で `./demo submit --wait`。`requests/demo.json` の 3 件を示す。8082 で `prstatusreports` のインスタンスを開き、モデル生成のタスクと依存関係を確認する。実際に表示された状態に合わせて説明し、未確認の並列数・時間短縮・トークン削減率は断定しない。

## 4. 結果を見る（約 1 分）

PASS の後に 8000 の `/report.html` を開く。模擬データの表示、PR リンク、CI 失敗、Draft、次のアクションを見る。モデルが生成するため、文面・レイアウトは実行ごとに変わりうる。

## 5. 同じ保存先へ再実行（任意）

完了後に `./demo submit --wait` を再実行。新しい ETag と、Blob の保存先が同じであることを示す。これは「安定した保存先への上書き」のデモであり、モデル出力の同一性を保証するものではない。

## ワーカー停止からの継続（任意・事前検証してから）

DTS/Azurite を止めず、実行途中でターミナル A の Ctrl+C → `./demo start`。エミュレーターを再作成してはいけない。DTS で再開の実結果を確認する。実行時間が短い場合は停止操作に間に合わないので、本編で必須にしない。

## 終了

ターミナル A の Ctrl+C、`./demo stop`、GitHub で Stop codespace。課金対象となる Codespace とモデルの利用を終了する。
